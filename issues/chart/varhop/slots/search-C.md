# Search: blind notes, slot C (2026-10-12)

Tiers: operator = INTAKE.md and Taken sections; better-than-training = inspected local source, primary docs/source, and the local Node probe below, all 2026-10-12; model-knowledge flagged where used.

## Facts inspected

- There is no shared fuzzy-search helper for third-party overlays. Each first-party surface hand-rolls matching, and none does full subsequence scoring: EmojiSearch.js:18-39 is lowercase substring over keywords with a result cap; ClipboardHistory.js:174-203 is lowercase substring over full text, newest first, cap 50; MenuModel.js:323-355 requires every query term to appear as a substring of name/aliases or as a whole word in the description, then tier-scores exact > whole-word > prefix > substring > alias > description with a stable order tiebreak; the dropdowns (Ui/SearchableDropdown.qml:75-86, Ui/MultiSelect.qml:136-148) are lowercase substring over label/description/value. The closest thing to ranking machinery is services/AppSearch.js (used only by AppLibrary.qml:54 for app entries): all terms must substring-match somewhere or match an acronym of word initials for terms up to 5 chars (AppSearch.js:42-69), scored in tiers name-prefix > id-prefix > name-substring > id-substring > haystack > acronym, ties broken alphabetically (:71-122). Varhop ships its own small matcher in the plugin; AppSearch is an internal service file, not a plugin API. [better-than-training]
- First-party list behavior to copy: query change resets selection to index 0 (Clipboard.qml:180-186); Up/Down wrap modulo the row count and scroll the selection into view with `positionViewAtIndex(..., ListView.Contain)` (:160-172); hover only moves the selection after real pointer movement through PointerMoveGate, so a stationary cursor under a freshly opened overlay does not steal the keyboard selection (:192-197,246); click selects and activates (:536-545 in the delegate MouseArea). Rows are a Rectangle delegate with selected colors and one elided Text line (`textFormat: Text.PlainText`) plus a preview pane for the selected row (Clipboard.qml:466-545). [better-than-training]
- fzf's default scoring rewards matched characters, penalizes gaps, and bonuses boundaries, delimiters and camel-case transitions, with a first-character multiplier (https://github.com/junegunn/fzf/blob/master/src/algo/algo.go lines 113-153, read 2026-10-12); its `path` scheme bonuses only after path separators (fzf.1, --scheme). VS Code's fuzzy scorer is the same family: character, consecutive, same-case, word-start and after-separator bonuses (https://github.com/microsoft/vscode/blob/main/src/vs/base/common/fuzzyScorer.ts lines 169-225, read 2026-10-12). Neither tolerates substitutions or transpositions; "fuzzy" in both means scored subsequence. [better-than-training]
- Raycast documents its root-search order explicitly: exact alias, alias prefix, title fuzzy score, subtitle/keyword matches, then frecency (frequency + recency) last, with a per-item Reset Ranking action (https://manual.raycast.com/search-bar, read 2026-10-12). Usage there reorders within the tail of the ranking, it does not outrank better text matches. [better-than-training]
- Diacritic folding probe (Node on this machine, 2026-10-12): `s.normalize("NFD")` with combining marks U+0300–U+036F stripped turns čćžš into cczs but leaves đ unchanged (U+0111 has no decomposition), and also leaves ł, æ, ß. "Džep" folds to "dzep" because ž loses its caron, so dž needs no digraph rule. Qt's QML JS engine implements the same ECMAScript `normalize`, so the fold used below is: lowercase, NFD, strip combining marks, explicit đ→d. [better-than-training]

## Q1 Fields and weights

Pick: precompute one folded search record per prompt at import: effective title (front-matter title, else prettified file name), aliases (file-name slug split on `-`/`_`/space, and each tag as its own string), category and subcategory (each segment as its own string), description, and body. Field weights, best term match wins per field: title 100; filename/tags 70; category/subcategory 50; description 30; body 10. Body is searched only as a folded substring (below). A prompt matches when every query term matches at least one field; terms may match in different fields.
Reason: the rank the operator acts on is "is this the prompt I named", and title/filename is the name they gave it. Tags are curated synonyms, so they rank just under title. Category is context ("the marketing one"), description is prose about the prompt, and body is a recall net for a remembered phrase. This is the same descending shape as MenuModel.js:341-355 and Raycast's documented order (Facts), generalized to varhop's fields. Per-atom fields (each tag, each path segment scored separately) stop a subsequence from spanning two tags and pretending to be one word.
Cost: body at weight 10 with substring matching can still return many rows for a common word; the result cap and per-term AND keep it below every structured match. Maintaining folded copies duplicates the library text in memory; at hundreds to low-thousands of prompts that is a few MB at most.

Rejected:
- Search title/name only (emoji-style). Reason: it throws away the metadata the repo-format fork made the author write, and a remembered phrase from the prompt body finds nothing.
- One concatenated haystack per prompt, AppSearch-style (AppSearch.js:22-25). Reason: field weighting disappears and subsequence matches can straddle field boundaries, ranking a category+tag accident above a title match.
- Full subsequence scoring over the body. Reason: O(query × body) per prompt per keystroke in JS buys noise; almost any short query is a subsequence of a long prompt. Substring is the honest body test: the user remembers words, not letter scatter.

Pitfalls:
- P1 Normalizing per keystroke. All folding, slug-splitting and word lists happen once per library import; per keystroke only the query is folded and scored. Remove: the importer emits the search record next to the display record.
- P2 Duplicate effective titles. Two prompts can share a title (same category, different files). Sort ties by full path and show the file name in the row's secondary line when the title came from front matter, so rows are always distinguishable.

## Q2 Matching and presentation

Pick: case-insensitive, diacritic-folded, multi-term AND, scored subsequence over the short fields (title, aliases, category, description), folded substring over the body. Per-field score for one term: whole-query phrase checks first (exact field, field prefix, word prefix, substring), then a greedy subsequence score with bonuses for word starts, post-separator and camel humps, and penalties for gaps and total span, in the fzf/VS Code shape, simplified to a linear scan. Presentation: ranked list under the search box, top row selected, updated on every keystroke with no debounce. No inline ghost completion of the top match.
Reason: the operator asked for instant fuzzy search with Google-like suggestions and arrow navigation (INTAKE.md; forks/search.md Carries). Scored subsequence over names is what makes "cem" find "Cold Email" and what both reference implementations do (Facts). Google's suggestions are themselves a ranked list under the box; a ghost completion adds an accept-key problem (Right already edits text in a real TextInput, Tab is spoken for in the editor stage) and makes the field show text the user did not type while copy-and-close gives that field native selection semantics.
Cost: no typo tolerance. A transposed query ("emial") finds nothing and the user retypes, which is cheap at this scale and keeps false positives out. [model-knowledge: subsequence is still found when a character is merely omitted, the most common slip while typing fast.] The greedy scorer can misrank rare cases an optimal alignment would catch; acceptable against DP scoring times fields times terms per keystroke.

Rejected:
- Prefix/word-prefix matching only (the first-party substring family). Reason: fails the operator's fuzzy requirement; initials and mid-word fragments are exactly how launcher queries look after two weeks of use. Menu and emoji search get away with substring because their items are short fixed labels, not user-authored titles.
- Edit-distance typo tolerance (fuse.js/Bitap style). Reason: at title lengths, one-edit tolerance admits near-miss prompts the user did not mean, costs a real algorithm in QML JS, and duplicates what retyping a 4-letter query does for free. Neither fzf nor VS Code quick-open does it (Facts).
- Smart case (uppercase in query means case-sensitive), fzf's default. Reason: prompt titles are prose, not code identifiers; a capitalized first letter from fast typing must not narrow the search.
- Đ folded to "dj" instead of "d". Reason: with a Croatian layout the user types đ directly; folding to d also matches a plain-d query. The "dj" ASCII fallback spelling is U1 below, not a silent extra rule.

Pitfalls:
- P3 Subsequence noise on 1–2 character queries. With one letter, everything "matches". Remove: subsequence scoring only applies from 2+ characters, and 1-character queries rank by prefix/word-prefix/substring classes only; body substring search needs terms of 3+ characters.
- P4 Body scan cost. Folded `indexOf` over every body on every keystroke is linear in total library bytes. Remove: run the body tier only when structured matches are fewer than the initial display chunk (Q4), so the common case never touches bodies; leaf criterion measures a 2,000-prompt fixture in the real shell, not Node.
- P5 Folded-index drift. Folding can change string length (decomposed input), so match positions in the folded string are not positions in the title. Remove: v1 rows show no per-character match highlights (first-party rows do not either, Facts). The one place that needs a position, the body snippet in Q4, derives its window from the folded body match and maps back by construction in the importer, or the snippet is cut from the folded text's neighborhood re-found in the original with a bounded search; leaf proves it on a č/đ fixture.

## Q3 Ranking signals and the empty query

Pick: two signals beyond text. First, usage: one record per prompt id in the state-dir file (never shell.json, sync-and-auth Taken), holding whole-prompt copy count and last-copied timestamp, written only when a Ctrl+C copy succeeds (copy-and-close's exit-0 moment). Usage is a bounded tie-break inside the same field-and-match class: coarse class (which field, exact/prefix/word/substring/subsequence) first, then usage (count desc, then recency desc), then fine score, then alphabetical by title, then path. It never lifts a body hit over a title hit. Second, the empty query: up to 10 most recently copied prompts first (recency order), then every remaining prompt sorted by category, subcategory, title; no section headers, the category path on each row carries the grouping.
Reason: Raycast puts frecency after all text signals (Facts) and that is the right humility for usage data: it should decide between two prompts the text cannot separate, not teach the launcher that a frequently used prompt matches every query. Counting copies rather than opens measures completed use; opens include wrong-prompt aborts. The empty list serves both jobs the operator has before typing: repeat the last thing (recents) or browse what exists (category order with paths visible). This answers C2 M3's empty-query and usage-store points.
Cost: a state file with ids and timestamps, written once per successful copy (atomic write, sync fork's volatile-state rule). Usage cannot help a prompt that was never copied rank above an equal unused one beyond alphabetics. Recents on an empty query are stale by design after days away; they are capped at 10 so the browse order takes over quickly.

Rejected:
- Usage as an additive score mixed into text score. Reason: unbounded feedback loop; a heavy-use prompt starts winning unrelated queries and the user cannot predict or inspect why. Raycast needed a Reset Ranking action to undo exactly this class of surprise (Facts).
- Empty query shows nothing until typing (pure Google box). Reason: kills browsing and the repeat-last-copy path, and makes a freshly connected repo look empty until the user guesses a word.
- Empty query grouped with category section headers. Reason: headers complicate the selection index and scroll math for information already printed on every row; sort order gives visual grouping for free.
- Store query history for suggestions. Reason: nothing asked for it, it persists what the user typed (including pasted values), and prompt suggestions already come from the library.

Pitfalls:
- P6 Usage keyed by path alone leaks across repos. The store is namespaced by the numeric repo id from the sync selection; a repo switch starts a fresh usage map, and ids no longer in the library are dropped on load. A renamed prompt is a new id and starts at zero, which is honest.
- P7 Usage write races the copy flow. The count updates at the same transition that discards the draft (copy exit 0); a failed or in-progress copy writes nothing. One writer, whole-file atomic write, no per-keystroke IO.
- P8 Draft row in recents. The draft prompt (copy-and-close: a draft can exist while search shows) can also be a recent. The draft marker in Q4 is orthogonal to ordering; the row appears once, in whichever position the rules give it.

## Q4 Result rows and keyboard

Pick: each row is two lines of plain text. Line 1: effective title. Line 2: `Category › Subcategory` (just `Category` when no subcategory), then ` · ` and the description when present; when the match came only from the body tier, line 2 instead shows a one-line snippet of the body around the first matched term, whitespace collapsed, so the user sees why it matched. Right-aligned on line 1: a `Draft` marker on the prompt holding the current draft, and nothing else. Front-matter parse errors show as a short warning suffix on line 2 (repo-format's lenient load made them visible somewhere; the row is where the user meets that prompt). No tag chips, no variable count, no icons.
Keyboard and list: a real `TextInput` holds focus (copy-and-close gives it native selection copy). Up/Down are intercepted on the TextInput itself (`Keys` BeforeItem on the attached item, per the variable-editing priority finding) and move the selection with wrap-around; PageUp/PageDown move by the visible page; Enter opens the selected prompt; typing resets the selection to the top row. Home/End stay text-cursor keys, unlike the clipboard catcher's list semantics, because there is a real cursor to move. Mouse: hover selects only after real movement (PointerMoveGate pattern, Facts), click opens, wheel scrolls without changing the selection until hover. Results render in chunks: first 50 rows, extended by 50 when the selection or scroll nears the end, with a footer count (`50 of 237`) whenever truncated; the full ranked array always exists in JS.
Manual pull while search is open: the query text and cursor stay untouched; the search reruns on the new library; the selection follows the previously selected prompt id if it still matches, otherwise clamps to the row now at the old index (or top when empty), and scrolls into view.
Reason: line 2 answers the two questions a user has at a row: where does this live, and why is it here. Category path plus description covers both for structured matches; the body snippet covers the body tier, which would otherwise look arbitrary. Chunked rendering keeps `ListModel.clear()`+append work per keystroke at 50 rows instead of thousands (clipboard caps at 50 for the same reason, Facts), while extending on demand keeps the empty-query browse complete, which a hard cap would silently break.
Cost: two-line rows show fewer results per screen than clipboard's one-liners; the card height is a style decision for the shell leaf. The body snippet is the only row content needing folded-to-original position mapping (P5). Preserving selection by id across a pull can jump the highlight far down the new ranking; that is the requested behavior (C2 M3), and scroll-into-view makes the jump visible rather than lost.

Rejected:
- One-line rows, title only. Reason: duplicate titles and body-tier hits become indistinguishable; the user opens prompts to check which one it was, which is the Notion round-trip this app replaces.
- Hard cap of 50 results with no extension. Reason: silently makes prompts 51+ unreachable by browsing and by broad queries; a hidden truncation in a launcher reads as "my prompt is gone".
- Render all rows into the ListModel per keystroke. Reason: clear+append of low-thousands of objects on every character is the main per-keystroke cost in the first-party rebuild pattern (Clipboard.qml:134-152 does it for 50); chunking removes it without changing behavior.
- Enter copies the top result without opening. Reason: contradicts INTAKE.md (a suggestion opens the whole prompt; variables may need values before any copy).

Pitfalls:
- P9 Selection identity is the prompt id (path), never a row index, anywhere state crosses a rebuild: query edits reset to top as a deliberate act, but library changes (pull) and chunk extension must not. Remove: one `selectById` path used by pull-rerun and by chunk extension; index is derived from id after each recompute.
- P10 The draft's prompt after a pull. Search rows come from the new library; the draft still holds its original template (copy-and-close Taken). The row can therefore show a new title while `Draft` resumes old text. Remove: the draft marker stays factual (a draft for that id exists); opening the row resumes the draft, and only discarding it and reopening gets the pulled text. No silent merge.
- P11 Long titles and two-line elision: both lines `ElideRight`, `textFormat: Text.PlainText` throughout, so a title containing `<b>` or `{` renders literally (first-party rows do the same, Facts).

## Questions the fork does not ask

- U1 The "dj" spelling for đ: should a query "djakovo" match "Đakovo"? My fold says no (đ→d). Supporting it cleanly means a second folded form per field (đ→dj) scored in parallel. Worth an operator word, since it depends on which keyboard layout the prompts are searched from.
- U2 Should query syntax exist in v1: quoted phrase, `cat:marketing`, `#tag`, exclusion? My picks assume plain space-separated terms only. Category-as-a-term already approximates `cat:` through the 50-weight field, but an operator who organizes by category may want a hard filter, which is a different contract.
- U3 Search variable names as their own field? "Which prompts take a CLIENT" is answerable today only as a body substring at weight 10. A parsed variable-name field at alias weight would make it a first-class query; the parser already produces the names for the editor.
- U4 After a successful copy ends the draft, does the next summon start with an empty query (my assumption, via fresh search in copy-and-close) or restore the last query and selected prompt? This fork and copy-and-close both touch it; one of them should own the sentence.
- U5 Should per-character match highlighting ship in v1 after all, accepting the folded-index mapping work (P5)? It is the main trust signal for subsequence ranking, and VS Code users expect it; first-party Omarchy rows set the opposite precedent.
- U6 Is there a reset for usage data (Raycast has one per item)? Deleting the state file works, but if the operator wants a visible control it belongs to settings-and-hotkey, which should hear about the store this fork creates.
