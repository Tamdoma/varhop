# Variable editing: blind notes, slot C (2026-10-12)

Tiers: operator = INTAKE.md and Taken sections; better-than-training = inspected local source, primary docs, measured probes read/run 2026-10-12; model-knowledge = flagged where used. No practitioner write-up on prompt-variable editing was found; the comparable-tool evidence below is primary documentation.

## Facts inspected

- No first-party Omarchy shell QML uses a multiline editor: `grep -rn 'TextEdit|TextArea' /usr/share/omarchy/shell --include='*.qml'` returns nothing. The only real text inputs are single-line password fields (plugins/lock/LockView.qml:165, plugins/polkit/PolkitAgent.qml:310). The varhop editor is new ground in this shell. [better-than-training, local grep 2026-10-12]
- First-party overlays instead hand-roll keyboard input: a `keyCatcher` Item with `Keys.priority: Keys.BeforeItem` builds the filter string from `event.text` one character at a time (plugins/emojis/Emojis.qml:188-239; same pattern in clipboard and menu). That pattern has no cursor, no selection, no paste, and drops multi-char IME commits. [better-than-training]
- `Keys.BeforeItem` on an ancestor runs before the focused descendant's own handling; /usr/share/omarchy/shell/Ui/PanelKeyCatcher.qml:23-32 documents this and its Tab handling treats `Key_Tab`+Shift and `Key_Backtab` as the same "previous" (:59-62). The clock panel shows the other working shape: `Keys.onPressed` inside a TextField intercepts Tab and selects the next field's text (plugins/panels/clock/Panel.qml:190-202,393,416). [better-than-training]
- QtQuick `TextEdit` (qt6-declarative 6.12.0-1, /usr/lib/qt6/qml/QtQuick/plugins.qmltypes, TextEdit component) offers `select(start,end)`, `insert`, `remove`, `positionToRectangle`, `inputMethodComposing`, `preeditText`, `textDocument`. It offers no protected or read-only text ranges. [better-than-training]
- Measured on this machine (PySide6, Qt 6.12, offscreen, 2026-10-12): `QTextDocument.setPlainText` then `toPlainText` converts CRLF and CR to LF, strips a leading U+FEFF, converts U+2028/U+2029 to LF, and preserves trailing newlines and tabs. So text read back from an editor document is not the stored body, and its character offsets are not the stored body's offsets after any CRLF. [better-than-training, probe]
- VS Code snippets: "Multiple occurrences of the same tabstop are linked and updated in sync"; `$0` is the final cursor position after the last stop; placeholder text "will be inserted and selected such that it can be easily changed" (https://code.visualstudio.com/docs/editing/userdefinedsnippets, source read 2026-10-12). [better-than-training]
- UltiSnips: "Mirrors repeat the content of a tabstop. During snippet expansion when you enter the value for a tabstop, all mirrors of that tabstop are replaced with the same value" (https://raw.githubusercontent.com/SirVer/ultisnips/master/doc/UltiSnips.txt §4.6, read 2026-10-12). [better-than-training]
- Espanso forms: `[[field]]` markers open a separate form window with one control per field, single-line by default (`multiline: true` opts in), submitted with Ctrl+Enter (https://espanso.org/docs/matches/forms/, read 2026-10-12). Raycast snippet arguments: up to 3 named arguments, required unless a default is set, collected before expansion (https://manual.raycast.com/dynamic-placeholders, read 2026-10-12). Both separate the field editing from the template text. [better-than-training]

## Q1 What can the user edit

Pick: variable values only. The body around them is fixed. One real `TextEdit` shows the whole rendered prompt (template with current values in place); a segment model parsed once from the original body owns the truth; an edit is accepted only inside the active variable's rendered range and becomes that variable's new value.
Reason: the operator's stated job is "focus on the variables and then easy way to copy", "something that changes the variables really fast" (INTAKE.md, operator). Nothing in the intake asks to reword the prompt, and the destination app is one paste away for one-off tweaks. Fixing the body removes a whole class: segment boundaries never move for non-variable reasons, copying is an exact rebuild (Q4), and a stray keystroke can never silently alter the template that gets copied. It also matches the carried lock that Tab order and values derive from the original template, never from re-parsed edited text (slots/map-merged.md:9).
Cost: no one-off body tweak before copying; the user pastes first and edits in the target. `TextEdit` has no protected ranges (Facts), so "values only" must be enforced by the plugin: an ancestor `Keys.BeforeItem` handler swallows editing keys when the cursor or selection is outside the active range, and an `onTextChanged` check against the expected render restores anything that slips through (context-menu paste, middle-click). That enforcement, including IME, is a leaf done-criterion (P2).

Rejected:
- Whole body editable, variables as tab stops in a free `TextEdit` (the VS Code snippet shape). Reason: VS Code's destination is the buffer itself; varhop's is a one-shot copy of a stored template. Free editing makes every boundary ambiguous after the first edit outside a stop (partially deleted `{{NAM`, text typed into braces), forces either re-parsing edited text (foreclosed) or range tracking through arbitrary edits, and lets one wrong keystroke corrupt the copied prompt unnoticed.
- Separate form fields, one input per variable, prompt shown as preview (Espanso forms, Raycast arguments). Reason: the operator locked in-place editing: "When the suggestion is clicked, the whole prompt opens", Tab "will move and select all those variables, including the braces" (INTAKE.md). A form also loses sentence context around each variable, which is what tells the user what value fits grammatically. The form's one advantage, simpler widgets, does not outweigh breaking the locked interaction.

Pitfalls:
- P1 Range enforcement fights IME composition. Dead keys and IME produce a preedit inside the active range before committing. Remove: while `inputMethodComposing` is true the guard accepts and the restore-check is suspended; the committed text is then attributed to the active value. Leaf proof with a dead-key sequence (for example ´ then c gives ć) and a pasted multiline value.
- P2 Edits that bypass keys: paste by menu or middle-click, undo/redo replaying a programmatic re-render. Remove: the `onTextChanged` verifier treats the segment model as truth and restores the expected render for any change not attributable to the active range; Ctrl+Z/Ctrl+Shift+Z are intercepted and applied to the active value's own history or ignored, never allowed to replay document states that predate a re-render (see U2).

## Q2 Stops: unique names, order, ends

Pick: one stop per unique variable name, in order of first appearance in the original body. The stop lives at the first occurrence; every other occurrence is a live mirror showing the same value. Clicking any occurrence activates that name and selects that occurrence's text, but Tab order never changes. Tab past the last stop wraps to the first; Shift+Tab before the first wraps to the last. Opening a prompt with variables selects the first stop immediately. A prompt with zero variables opens ready to copy; Tab does nothing.
Reason: repo-format already locks "repeated names share one value", so per-occurrence stops would make the user tab through stops they cannot change independently. Linking same-name occurrences is what both snippet systems with in-editor stops do (VS Code linked tabstops, UltiSnips mirrors, Facts). Wrapping keeps Tab always meaningful for review-before-copy, and Ctrl+C already exists as the exit, so no final position is needed.
Cost: a user who habit-Tabs after the last variable lands back on the first and could retype over it; the filled-state marking in Q3 and a filled count are the guard. Clicking a mirror then pressing Tab goes to the next unique name, not the next visible occurrence, which is one rule to learn.

Rejected:
- One stop per occurrence. Reason: contradicts the shared-value lock in spirit and wastes keystrokes; VS Code and UltiSnips both collapse repeats into one stop with mirrors.
- Tab on the last stop moves to a final cursor at the end of the text (VS Code `$0`). Reason: in VS Code that lands the user in a real editable buffer; here the body is not editable (Q1), so the final position is a place where no key does anything useful.
- Tab on the last stop copies and closes. Reason: it turns a navigation slip into a finished action with the overlay gone. Copy already has its own key from every stage.

Pitfalls:
- P3 Shift+Tab arrives as `Key_Backtab` on some layouts and as `Key_Tab` with ShiftModifier on others. Remove: accept both, exactly as PanelKeyCatcher.qml:59-62 and ImagePicker.qml:708-711 do.
- P4 Mirror edits shift every later offset. Remove: offsets are recomputed from the segment list on every render, and mirrors are patched back-to-front with `insert`/`remove`; no offset is cached across an edit.
- P5 A stop below the fold. Remove: on every stop change scroll the `cursorRectangle` into view; long prompts in a small overlay are the normal case, not an edge case.

## Q3 Visible state, revisiting, reset

Pick: the view is one rendering rule at all times: an unset variable shows its `{{NAME}}` token, a set variable shows its value in place with a persistent filled marker (highlight behind the value's range, using `positionToRectangle` geometry), and the active stop's whole rendered text, token including braces or current value, is selected. Typing or pasting over the selection starts the value; further typing edits it as plain text inside its range. Revisiting a set stop re-selects the whole value, so retyping replaces and arrow keys or a click place the cursor for a partial fix. Reset is the same gesture as clearing: with the whole value selected, Delete or Backspace returns the variable to unset and the `{{NAME}}` token reappears. There is no separate reset key. Enter moves to the next stop like Tab; Shift+Enter inserts a newline into the value; pasted multiline text is always accepted as-is.
Reason: selected-placeholder-replaced-by-typing is the snippet behavior users already know (VS Code placeholder "inserted and selected such that it can be easily changed", Facts), and the operator locked the selection-includes-braces behavior (INTAKE.md). Deriving the reset from "delete the selected value" means one mental model: a variable is a piece of text that is either the token or your text. Enter-as-next matches form behavior in Espanso (Ctrl+Enter submits) weakened to per-field advance, because most prompt values are single-line; the escape hatches for multiline are explicit.
Cost: an intentionally empty value cannot be copied in v1; clearing always means "back to unset", and what copy does with unset variables is copy-and-close's call (Q4 defines the rebuild either way). Enter inserting a newline requires Shift, which will surprise a user typing a multi-paragraph value by hand once. The filled marker for a value that wraps across lines needs one highlight rect per visual line; if that proves flaky in the leaf, the fallback is active-stop selection only, with unset tokens still self-evident from their braces.

Rejected:
- Filled value shown but no longer marked or revisitable as a stop ("burned in" once typed). Reason: the user cannot fix a typo or swap a value after reviewing later context, which the hide-and-resume workflow in INTAKE.md (go find a value in the browser, come back) depends on.
- Keep `{{ }}` braces around filled values in the view (for example `{{Ivan}}`). Reason: the view should read as the final prompt the user is about to copy; braces that will not be copied invite misreading, and editing "inside the braces" reopens partial-token states Q1 removed.
- A dedicated reset shortcut (for example Ctrl+Backspace on a stop, or reset-all key). Reason: Delete on the automatically-selected value already is that gesture; reset-all is Esc to search and reopen, which copy-and-close owns.

Pitfalls:
- P6 Selection state after hide and resume. The overlay can be hidden mid-edit (INTAKE.md); on resume the active stop must be re-selected and focus restored with `forceActiveFocus`, or the first typed character goes nowhere. Remove: draft state (active stop index) is part of the draft model, reapplied on every show.
- P7 Cursor at a range boundary. Define the active range as inclusive of both ends for typing, so pressing Left from a fresh selection then typing extends the value at its start instead of hitting the Q1 guard. Remove: boundary rule written into the guard, covered by the Q1 leaf proof.

## Q4 Copied text and token grammar

Pick: copied text is rebuilt from the stored original body and the values map, by concatenating segment slices: literal segments exactly as stored (with `\{{` escapes processed as below), set variables replaced by their value text, unset variables replaced by their original `{{NAME}}` token text. The editor's `text` is never read for copying. One leading U+FEFF is stripped at import time (repo-format's importer), so the stored body is already BOM-free.
Reason: the measured Qt behavior (Facts) means the editor document silently normalizes CRLF, CR and U+2028/U+2029 to LF and strips a BOM. Reading copy from it breaks the repo-format lock "prompt bodies are arbitrary Markdown and are copied verbatim" (forks/repo-format.md:28) for any Windows-authored or pasted file. Rebuilding from segments keeps the stored string bit-exact from import onward: JS string slices of the original are concatenated, values spliced between them.
Cost: two renderings exist, display and copy, and they differ wherever Qt normalizes. All selection offsets for the `TextEdit` must be computed on a display string built from the same segments with CRLF normalized to LF, while copy uses the unnormalized segments. One segment list feeding both builders is the mechanism; a CRLF fixture whose Tab selections land exactly on tokens is the leaf proof (P8).

Grammar, pinned. A token is `{{` + NAME + `}}` where NAME matches `[A-Z_][A-Z0-9_]*`. Scanning is a single left-to-right pass over the original body; at each `{{` the token match is tried once.
- `{{2NAME}}`, `{{123}}`, `{{ NAME }}`, `{{}}`, unclosed `{{NAME}`: literal text (first char must be a letter or underscore, the usual identifier shape; `{{PAGE_404}}` covers the digit case).
- `{{{NAME}}}`: literal `{`, token `{{NAME}}`, literal `}`. No triple-brace meaning.
- `{{NAME}}}`: token plus literal `}` (first `}}` closes).
- `{{A{{B}}}}`: `{{A` fails to match, stays literal; `{{B}}` is the token; trailing `}}` literal. Follows from the single-pass rule, no nesting.
- `\{{NAME}}` with a valid NAME: literal `{{NAME}}` in both view and copy, backslash consumed. `\` before anything that is not a valid token opener (including `\{{abc}}`) is a literal backslash, copied as-is. So the escape exists only where a token would otherwise form.
- Tokens inside Markdown code fences or inline code are stops. The escape is the way to show a literal example. No Markdown awareness in the scanner.
- Typed or pasted `{{OTHER}}` inside a value stays literal (carried lock): traversal and segments come only from the original parse.

Rejected:
- Read the copied text from the `TextEdit`. Reason: measured normalization above; it also makes copy depend on the Q1 guard never having leaked an edit.
- NAME as `[A-Z0-9_]+` with any first character. Reason: `{{2024}}` or `{{404}}` in template examples become surprise stops; every template language's identifier rule (letter or underscore first) is what authors will assume. The repo-format Taken lists the character set, not the first-char rule, so this pins rather than reopens it.
- Code-fence-aware scanning (skip tokens inside fences and inline code). Reason: a second parser (fenced ```, ~~~, indented blocks, inline spans) whose misses are silent, and prompts frequently place real variables inside code they ask the model to emit. The one-character escape is cheaper and total.
- String `replace()` for substitution. Reason: JS replacement strings treat `$&`, `$'`, `$$` specially; a value containing `$&` would corrupt the copy. Concatenation of slices has no such case. [model-knowledge, JS semantics]

Pitfalls:
- P8 Offsets computed on the original string but applied to the display document select the wrong text after the first CRLF (measured above). Remove: segment list carries both original offsets (copy builder) and display offsets (editor), generated in the same pass with the LF normalization applied only to the display copy.
- P9 Surrogate pairs: JS string indexes and Qt cursor positions are both UTF-16 code units, so emoji in values do not shift offsets as long as nothing counts Unicode code points. Remove: leaf fixture with an emoji before a token; forbid `Array.from(str)` style code-point iteration anywhere offsets are computed.
- P10 Front matter carry: the editor's "original body" is the post-front-matter body from repo-format's importer, under its boundary rule (a body opening with `---` must not be swallowed, CHART.md Fog). If the importer mis-strips, this fork faithfully edits the wrong text. Remove: the importer's boundary fixture ships in the repo-format leaf; this fork only consumes its output.

## Questions the fork does not ask

- U1 Is Enter-as-next-stop (my Q3 pick) actually what the operator wants, or should Enter insert a newline and only Tab navigate? This decides the feel of long pasted or hand-typed values and is an operator taste call with real costs both ways.
- U2 Undo scope: per-value undo while a stop is active, whole-draft undo, or no undo in v1? The segment model makes whole-draft undo a values-map history, which is easy, but it will not match muscle memory of document undo after a mirror patch.
- U3 Should values persist per prompt across sessions (last-used value for `{{CLIENT}}` pre-filled next time), or is every open a blank template? Snippet tools start blank; prompt reuse may not want to. This touches settings/storage, so it should be asked before the settings fork, not after.
- U4 Clicking ordinary body text: place a cursor that can only select and copy text (interacts with copy-and-close's Ctrl+C), or snap the click to the nearest variable stop? My Q1 guard allows selection anywhere for reading; the click's job needs one sentence.
- U5 Is there a size ceiling? A multi-thousand-line prompt or a pasted whole-article value re-renders on each keystroke through string concatenation and mirror patching. Fine at expected prompt sizes; if the operator's Notion prompts include very large ones, that changes the render strategy and should be measured, not assumed.
