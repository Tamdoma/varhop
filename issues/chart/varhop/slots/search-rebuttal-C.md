# Search: rebuttal C (disagreements only, 2026-10-12)

RC1. D-a body search: hold A,C, with C's restrictions as the contract. B's rejected O2 is equal-weight or full fuzzy body search; that is not the proposal. Body is folded substring only, every term must hit, terms under 3 chars never reach it, it ranks below every structured field, and it runs only when structured matches are fewer than the first display chunk. B's alternative makes optional front matter (repo-format Taken: title, description and tags are all optional) effectively required for content recall: a prompt with a bare filename and a good body becomes findable only by words the author happened to put in the filename. First-party precedent also treats content as searchable text where the content is the item (ClipboardHistory.js:160-202 substring over entry text). The cost B names is real but bounded and testable, and the agreed real-shell latency proof is where it gets paid.

RC2. D-b usage: hold A,C. B's own Q7 supplies the contract if usage is chosen (successful whole-prompt copy, identity plus count/time, no query or body), and C's repo-id namespacing closes the identity hole B lists in R6. What remains of B's objection is a preference for a fully static order. Against that: the operator asked for Google-like suggestions (INTAKE.md), and under this design the order changes only when the user completes a copy, never on opens, hovers or keystrokes, and never across a match-class boundary. One correction to my own notes within this position: the usage key should be a decayed frecency (recent copies weigh more), not lifetime count first, or an old heavy prompt wins its class forever. A's "decayed" qualifier (search-A.md Q3) should be explicit in the merged contract.

RC3. D-c row line 2: the merge drops half of C's position. C already requires the file name in line 2 when the title came from front matter (search-C.md P2), so the live dispute is narrower: B shows the filename always, C shows it when it carries information the title does not (front-matter title, or a duplicate title in the library), and drops it when the title is just the prettified filename. Concede B's inclusion in those cases; hold the body snippet for body-only hits. If D-a stands, a body-tier row with only path+filename+description is an unexplained result, the exact failure the snippet removes.

RC4. D-d rendering: concede B. `ListView` instantiates delegates on demand (B E10), so an all-matches model does not mean all rows are built; my chunking was guarding `ListModel` append cost that a direct array model may not have. Keep a total-match count in the footer for broad queries either way. Chunked extension should return only if the agreed latency proof fails without it.

RC5. Resume (B Q8): agree, with a visible shape. A shortcut alone is undiscoverable, and the draft row can be filtered out by the query or deleted by a pull (B R8), so search should pin a "Resume draft" action above the results whenever a draft exists, distinct from result rows and outside ranking. The key binding stays owed to settings-and-hotkey next to "Find another prompt", but the search fork should record the pinned action as its contract; otherwise the only route back is Esc to hide, then summon, which works by accident of the lifecycle rather than by anything on screen.

RC6. Tag correction, Agreed pull fallback: merged says a manual pull keeps the selection by id "else top" (A,B,C). C proposed clamping to the row at the old index, not top (search-C.md Q4). Concede to A,B anyway: when the selected id is gone, the best current match is a more predictable Enter target than whatever inherited the old position.
