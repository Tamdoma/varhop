## Facts inspected

- `Quickshell.clipboardText` is a settable string (/usr/lib/qt6/qml/Quickshell/quickshell-core.qmltypes:998-1005), but no first-party shell QML uses it (grep over /usr/share/omarchy/shell, 2026-10-12). Quickshell 0.3.2 docs warn that under Wayland the clipboard reads empty unless a Quickshell window is focused (https://quickshell.org/docs/v0.3.2/types/Quickshell/Quickshell/, clipboardText). Every first-party copy path goes through `wl-copy`: helpers in /usr/share/omarchy/bin/omarchy-clipboard-paste-text:39,50 and inline `printf %s … | wl-copy` in panels/network/Panel.qml:495 and panels/tailscale/Service.qml:109. [better-than-training]
- `omarchy-clipboard-paste-text` with direct text takes it as argv (`text=${1:-}`, :48-50); with `--history-index` it pipes from the history file through jq into wl-copy (:38-39) and never puts text in argv. `--copy-only` exits after copying; without it, the helper sleeps 0.15 s and pastes with `wtype -M shift -k Insert` (:57-62). The clipboard overlay's Enter applies (copy + Shift+Insert), Shift+Enter copies only (plugins/clipboard/Clipboard.qml:226-233 and applySelected above it). Emoji insert copies with `wl-copy --sensitive --foreground`, pastes, then kills the copy owner so nothing stays on the clipboard (/usr/share/omarchy/bin/omarchy-menu-emoji-insert:13-20). [better-than-training]
- Quickshell `Process` can feed wl-copy without argv or a shell: `stdinEnabled` plus `write(string)`, and setting `stdinEnabled` back to false closes the stdin channel for that run (https://quickshell.org/docs/v0.3.2/types/Quickshell.Io/Process/, read 2026-10-12). wl-copy reads stdin to EOF, forks a background owner, and its parent exits; `--trim-newline`, `--paste-once`, `--sensitive`, `--type` are its options (`wl-copy --help` on this machine). [better-than-training]
- Whatever varhop copies the ordinary way lands in Omarchy clipboard history. The clipboard plugin runs `wl-paste --type text --watch` under a death-signal wrapper (plugins/clipboard/Clipboard.qml:284-291), stores up to 500 entries in ~/.local/state/omarchy/clipboard-history.json (:41,77), and its capture script skips only clipboard data hinted sensitive (plugins/clipboard/capture.sh:15-17). A regular wl-copy from varhop is captured like any other copy. [better-than-training]
- Hide is not unload. A keepLoaded panel's Loader stays active while hidden (shell.qml:1394); `hide()` calls the plugin's `close()` and removes its open id (shell.qml:1213-1227), so instance state survives hide/show. A full plugin reload is different: `reloadPlugins()` calls `unloadPanels()`, which clears the entry model and loaders (shell.qml:1509-1518,1266-1272). Only keepLoaded *services* are preserved across that reload, not panels (shell.qml:1051-1054). A local plugin file change (which is what `omarchy plugin update` produces) schedules exactly this reload (shell.qml:1531-1536 plus the inotify watcher in services/PluginRegistry.qml). [better-than-training]
- First-party overlay key habits: Esc clears the filter if one is set, else closes (plugins/clipboard/Clipboard.qml:355-358, same shape in emojis). `open()` resets filter, selection and cursor every summon (Clipboard.qml:43-51). Varhop's resume requirement means its `open()` cannot copy that reset. [better-than-training]
- Launchers split on paste vs copy: Raycast lets the user set Search Snippets' primary action to "Paste to Active App" or "Copy to Clipboard", and its snippet arguments are required unless a default exists (https://manual.raycast.com/snippets, https://manual.raycast.com/dynamic-placeholders, read 2026-10-12). Alfred's clipboard viewer pastes on Return by default, keeps a persistent clipboard history, and ignores concealed/password-app data (https://www.alfredapp.com/help/features/clipboard/, read 2026-10-12). Espanso expands in place where the trigger was typed, so there is no target ambiguity (https://espanso.org/docs/matches/forms/, read 2026-10-12). Walker/elephant are not installed on this machine (`command -v` finds neither), so the local launcher precedent is the first-party overlays above. [better-than-training]

## Q1 What Ctrl+C copies, how, and whether it pastes

Pick: Ctrl+C in the editor (subject to Q3) copies exactly the rebuilt prompt: original body segments as imported (front matter already stripped by the importer), set variables replaced by their values, empty values as nothing, unset variables as their `{{NAME}}` text (all per variable-editing Taken). No title, no front matter, no trailing-newline trimming. It reaches the clipboard through a dedicated Quickshell `Process` running `wl-copy --type text/plain` fed on stdin: start with `stdinEnabled: true`, `write(rebuiltText)`, set `stdinEnabled: false` to close stdin, and only when that process exits 0 does the overlay hide and the draft get discarded. It does not paste into the previously focused app.
Reason: wl-copy is the only copy mechanism first-party shell code uses, and its forked background owner keeps serving the selection after the overlay and even the shell plugin are gone, which is the whole point of copy. Feeding stdin through `Process` keeps the prompt out of argv (the direct-text helper path exposes it in the process list and caps its size, Facts) and out of a `bash -c` quoting round-trip like the network/tailscale panels use. Waiting for exit 0 makes close-on-copy honest: if wl-copy fails, the overlay stays, the draft stays, and the footer shows the error instead of the user discovering an empty clipboard in the target app.
Cost: one Process spawn per copy and a close delayed by its exit (milliseconds; wl-copy only has to read stdin and fork). The stdin-close behavior of `stdinEnabled` needs a leaf proof (P1). Byte-exactness of `write(string)` to wl-paste for CRLF, NBSP, emoji and a final newline is part of that proof.

Rejected:
- `Quickshell.clipboardText = text`. Reason: unused by any first-party code, and its Wayland behavior is tied to a focused Quickshell window per the docs warning (Facts). The overlay is focused at set time but is then hidden; whether the selection survives hide and a later plugin reload would rest on Qt's data-device behavior, while wl-copy's independent owner process has no such coupling.
- `omarchy-clipboard-paste-text` with the prompt as its argument. Reason: argv exposure and size cap (Facts). Its `--history-index` path avoids argv but only copies text already in clipboard history, which would require putting the prompt there first.
- Copy and auto-paste into the previously focused app (the clipboard overlay's Enter behavior, Raycast's "Paste to Active App", Alfred's paste-on-Return). Reason: those tools act in one step from where the user summoned them. Varhop's locked workflow deliberately breaks that link: the user hides the overlay, browses Chrome for a value, and comes back (INTAKE.md), so "previously focused" at copy time may be the browser field they copied from, not the prompt's destination. Auto-paste of a multi-line prompt also fires into whatever has focus; in a terminal without bracketed paste each line executes. [model-knowledge for bracketed-paste behavior] The operator asked for Ctrl+C, a clipboard semantic, and one manual paste keystroke buys a known target.

Pitfalls:
- P1 `Process.write` then close: if `stdinEnabled: false` is set before the write flushes, wl-copy gets a truncated or empty stdin. Remove: leaf proof copies a fixture with CRLF, NBSP, emoji and final newline and compares hashes via `wl-paste --no-newline` in a test seat/session, without touching the operator's real clipboard.
- P2 Empty rebuilt prompt (empty body, or one variable set empty and nothing else): wl-copy with empty input does not produce a usable copy, and closing would silently drop the draft. Remove: an empty rebuild is refused in place with a footer note ("nothing to copy"); clipboard and draft are both untouched.
- P3 IME preedit at Ctrl+C: the active value may hold uncommitted composition the user can see but the values map does not. Remove: Ctrl+C first commits through the input method (`Qt.inputMethod.commit()`) and rebuilds after commit resolves; proven with a dead-key sequence in the variable-editing leaf proof list.
- P4 History capture: the copied prompt, values included, becomes a persistent clipboard-history entry (Facts). This is the same treatment as any copy the user makes anywhere and lets them recover a missed paste, so I accept it deliberately and do not pass `--sensitive`. The cost is stated here, not hidden; U1 asks whether the operator wants otherwise.

## Q2 Unset variables at Ctrl+C

Pick: copy anyway, unset variables as their `{{NAME}}` token text, no warning step and no block. The unset count is always visible in the editor (braces on every unset token, plus an "N unset" footer count while editing), so the warning exists before the key is pressed, not as an interruption after it.
Reason: copying a partially filled template is a real use (fill the rest in the target, share the skeleton, fill a value the editor cannot hold yet), and empty-vs-unset already gives the user both "deliberately blank" and "not yet". The operator's stated design center is speed with no extra buttons (INTAKE.md); a confirm step taxes every intentional partial copy to save an occasional overlooked token that is visibly braced in the text in front of them.
Cost: a user who misses a variable below the fold pastes `{{NAME}}` into their AI tool and notices there. The always-on count is the mitigation; there is no second chance after close except clipboard history (P4 makes recovery possible).

Rejected:
- Block copy until every variable is set (Raycast's required arguments, Facts). Reason: Raycast collects at most 3 arguments in a form before expanding; varhop variables are unbounded in-place slots, and blocking forces junk values into optional variables just to get the text out. Nothing in INTAKE.md asks for validation.
- Warn and require a second Ctrl+C ("2 unset, press again"). Reason: introduces a modal state machine (what resets it: typing? Tab? a timeout?) on the primary exit path for a condition that is already displayed. If this is ever wanted it is a settings toggle later, not a v1 default.

## Q3 Ctrl+C with a selection

Pick: behavior splits by stage and by what the selection is.
- Search box or any settings text field: Ctrl+C is the native control's copy of the selected text; the overlay stays. With no selection it does nothing.
- Editor: if the selection is exactly the active stop's auto-selected range, or there is no selection, Ctrl+C means the operator's locked action: copy the whole rebuilt prompt and close (Q1). If the user has made a different selection (dragged, or shift-extended across prose or part of a value), Ctrl+C copies that selected displayed text and the overlay stays open with the draft untouched.
Reason: the whole-prompt flow covers every state variable-editing produces on its own: first stop auto-selected on open, selection collapsed after typing, next stop auto-selected on Tab. Those all resolve to "whole prompt", so the locked gesture never surprises in the main workflow. The only way to get the other branch is a deliberate selection action, and native copy is what a deliberate selection means in every editor the user has. Copying a value or a phrase out of the prompt (into a browser search, into another variable) is a plausible mid-edit need in exactly the hide-and-seek-values workflow INTAKE.md describes.
Cost: exact-equality is a heuristic. A user who manually selects precisely the active value and presses Ctrl+C gets the whole prompt and a closed overlay instead of the value. After a selection copy, the selection is still there, so a second Ctrl+C copies the selection again; reaching the whole-prompt copy takes a Tab or cursor move first. Both costs are bounded and learnable; the alternative costs below are worse.

Rejected:
- Ctrl+C always copies the whole prompt in the editor, selection ignored. Reason: it destroys the standard meaning of an explicit selection and makes one reflex keystroke (copy this bit) close the overlay and discard the draft. That is the failure C2 M2 flagged.
- Ctrl+C always copies the selection when one exists. Reason: on open and on every Tab the active token is auto-selected (variable-editing Taken), so the most common Ctrl+C of all, "take this prompt now", would copy a single token and stay open. This breaks the operator's locked gesture in its main path.
- Move whole-prompt copy to a different chord (for example Ctrl+Shift+C) and leave Ctrl+C fully native. Reason: it reopens an explicit operator decision ("The Ctrl plus C button will copy the entire prompt", INTAKE.md) to solve a conflict the stage split already solves.

Pitfalls:
- P5 Selection equality must be measured against the stop range the plugin itself set, in display coordinates, at key time, not inferred from text content. Remove: the plugin records `autoSelectedRange` whenever it programmatically selects a stop and clears that record on any user selection change (`selectionStart/End` moving without a programmatic call); Ctrl+C compares against the record.
- P6 Selecting the whole value by double-click or Ctrl+A in a single-line value can coincidentally equal the stop range. This is the stated cost, not a bug; U2 asks whether the operator would rather have the always-native rule with the open/Tab states exempted instead.

## Q4 Esc, summon, and draft survival

Pick, as one state machine with a single draft kept in memory in the keepLoaded plugin instance:
- Esc in the editor: back to search. The draft is kept, tied to its prompt id and the template text it was opened from. The search shows that prompt's row marked as holding a draft (mechanism is search-fork presentation; the state is owned here).
- Esc in search: if the query is non-empty, clear it (first-party habit, Facts); if empty, hide the overlay. A draft underneath is never touched by search-stage Esc.
- Hide (hotkey toggle, click on the scrim, Esc closing search): hide only. Stage, query, active stop, cursor and selection remain exactly as left, per variable-editing Taken (resume keeps exact cursor and selection).
- Summon: show the current state as-is. With a draft whose stage is the editor, that means the editor resumes; with no draft, a fresh empty search. `open()` is idempotent and never resets anything; a repeated summon while already open changes nothing.
- Opening a different prompt from search discards the existing draft at the moment the new prompt opens. That deliberate selection is the discard action; there is no confirm. Reopening the draft's own prompt resumes it (values, active stop, cursor, selection, scroll).
- Successful Ctrl+C whole-prompt copy discards the draft (Q1). Selection copy, failed copy, Esc and hide never do.
- Draft survival boundary: the draft survives hide/show and theme changes (theme colors flow through watched files into bindings; the panel instance is not recreated). It does not survive a plugin reload, a plugin update, or a shell restart, because all three destroy the panel instance (Facts). This boundary is stated in the fork, not discovered by the user.
Reason: keepLoaded gives hide/resume for free and truthfully: the Loader stays active while hidden (shell.qml:1394), so "exact cursor and selection" is just not touching the instance. Back-to-search on Esc matches every stacked view the operator has used, while keeping the draft removes the one expensive accident: values were gathered from other apps, and an Esc reflex should not throw them away. Anchoring the draft to the id and template it was opened from keeps a manual pull (sync-and-auth: refresh never changes the open draft) from silently reinterpreting values against a changed template; after a pull, reopening that prompt is a new template and starts fresh.
Cost: one draft maximum. A user mid-draft who wants a second prompt first must copy or abandon the first by opening the second. There is no explicit "discard this draft and reopen the same prompt blank" gesture except opening another prompt and coming back; U3 raises whether that deserves a key. Memory-only means a shell crash during a long hide loses the gathered values; the rejected persistence below prices that honestly.

Rejected:
- Esc in the editor hides the overlay (same as toggle). Reason: then there is no keyboard path back to search to pick a different prompt, and Esc meaning "leave entirely" in the editor but "clear then leave" in search is fine, while Esc meaning two different kinds of leave by stage is not.
- Esc in the editor discards the draft and goes to search. Reason: prices an accidental keypress at all gathered values. Deliberate discard already exists (open another prompt, or copy).
- Summon with a draft starts a fresh search and keeps the draft only as a row marker. Reason: the reason the user summoned after hiding mid-edit is to continue editing (INTAKE.md's browser trip); forcing a search round-trip to get back taxes the core workflow to serve the rarer "new prompt" case, which Esc already serves from the resumed editor.
- Persist the draft to a state-dir file so it survives reload/update/restart. Reason: it writes potentially large pasted values to disk in plain text on every edit, and restoration must validate prompt id, template revision and repo identity, then decide what a days-old resurrected draft means against a manually pulled new template. The losses it prevents (crash or update during a hide) are rare and user-initiated in the update case. If the operator wants cross-restart drafts, that is a settings-and-storage decision with its own file contract, not a default.

Pitfalls:
- P7 `close()` naming: the host calls the plugin's `close()` on hide (shell.qml:1222). Varhop's `close()` must only mark itself not-open; if it also cleared draft or stage (as clipboard's `close()` clears transient dialog state, Clipboard.qml:53-56), every hide would eat the draft. Remove: draft clearing lives only in the copy-success and open-different-prompt transitions, and a leaf test hides via the host path, not just the plugin's own dismiss.
- P8 Focus and selection on resume: the overlay surface is recreated per show (OverlayWindow in form-factor Findings), so the editor item persists but keyboard focus does not. Remove: on show, after the window reports ready, `forceActiveFocus()` on the editor and reapply the recorded cursor/selection; leaf proof types immediately after summon and lands in the resumed value.
- P9 Stale draft against a pulled template: user hides mid-draft, later opens settings and pulls, template changes. Remove: the draft records the exact template string (or its hash); resume shows the draft against its own recorded template, and only a fresh open from search picks up the new text. The draft never re-parses.

## Questions the fork does not ask

- U1 Should varhop's copies be marked sensitive so Omarchy clipboard history skips them (capture.sh:15-17 honors the hint), at the cost of a missed paste being unrecoverable from history? Values can contain things pasted from elsewhere. My pick is no (Q1 P4), but it is the operator's privacy call.
- U2 Q3's equality heuristic vs fully native editor Ctrl+C with only the auto-selected states exempted by construction: I merged those into one rule. If the operator ever copies a whole selected value on purpose, they will hit my cost case. Is a separate visible "copy selection" affordance (for example Ctrl+Shift+C for selection, documented in the footer) wanted instead of inference?
- U3 Is there an explicit discard-draft key (editor and search-row), or is "open a different prompt" discard enough? Related: after Esc to search, should reopening the draft prompt ask fresh-vs-resume ever, or is resume always right?
- U4 A separate copy-and-paste action: Q1 rejects auto-paste for Ctrl+C, but a distinct chord (for example Ctrl+Enter in the editor) that copies, closes and Shift+Inserts into the focused app mirrors the clipboard overlay's Enter/Shift+Enter split (Facts). Not requested in INTAKE.md; ask rather than assume, and it belongs with the hotkey inventory in settings-and-hotkey.
- U5 After a whole-prompt copy closes the overlay, should the next summon remember the last search query or last prompt (not the draft, just position)? First-party overlays reset fully (Clipboard.qml:43-51). My Q4 pick resets to a fresh search because there is no draft; whether search itself remembers is a search-fork question, flagged here so the two forks do not decide it twice.
