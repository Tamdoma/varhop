# repo-format rebuttal (slot C), disagreements only. Read 2026-10-12.

RC1 Q1 content root (merged:5, 27). Not an operator question. `prompts/` default (A,B) and my optional `root:` key are the same design with a different default: default root `prompts/`, `root:` in the marker overrides it for a repo that keeps prompts elsewhere. Root-level `.md` files are then never prompts by either rule. Record it as settled in that form, not as "`prompts/` vs repo root".

RC2 Q2 sidecar (merged:11, 27). Disagree with listing "YAML front matter vs JSON sidecar" as operator-owned. The sidecar moves the `vars` map (default, hint) into a file separate from the body it annotates, doubles files, and makes every rename or move two edits; in a copy-fast tool authored in a text editor that is the Notion tedium again. B's stated reason, "QML has no YAML library, so YAML means a hand-written parser", is a cost both sides already accept: the shell itself hand-parses TOML for user-supplied data (/usr/share/omarchy/shell/Commons/Color.qml:184-205) and every surveyed prompt-file format puts metadata in front matter (VS Code prompt files, dotprompt, Hugo; URLs in slots/repo-format-C.md Evidence, read 2026-10-12). Put the one-line choice to the operator with front matter as the recommendation, not as an open pair.

RC3 Q3 invalid `{{` errors (merged:15). Disagree with B's "error on an invalid unescaped `{{`". Under the name rule the merge leans to (uppercase only, merged:16), a non-matching `{{...}}` is the designed way to write literal braces without an escape; erroring on it makes every prompt that quotes Handlebars, Jinja or Mustache (`{{#if}}`, `{{ item }}`) fail to load. Mustache itself has no escape and only delimiter switching (mustache.github.io/mustache.5.html, 2026-10-12), so prompts about templating will contain such text. Literal stays literal; `\{{NAME}}` is only for the uppercase form.

RC4 Q3 defaults (merged:18, 27). Disagree with framing "defaults yes/no" as a v1 UI question that decides the format. Reserving the front matter key (`vars: NAME: {default, hint}`) costs nothing even if the v1 UI ignores it, and not reserving it means the first repo that wants a hint needs a format bump. Record: the format reserves `vars`; whether v1 UI renders hints is a variable-editing question, not a repo-format one.

RC5 Q4 marker (merged:21). Disagree with "cost of none: a future v2 detects v1 by absence". Absence only identifies v1 if v2 makes the marker mandatory, which breaks every v1 repo at the bump; and using `prompts/` as the marker conflates content root with format version. B's required `varhop.json` rejects a perfectly good repo that lacks one file. The optional marker (`format`, `root`) covers both: absent = v1 at `prompts/`, present = explicit, higher `format` = one top error with best-effort load. Also record that it answers RC1.

RC6 Strictness (merged:24, 27). Disagree that strict-whole-revision is an equal option for the operator to weigh. Omarchy's own precedent splits by kind: strict for code at install time (omarchy-plugin-validate runs before a plugin is placed, /usr/share/omarchy/bin/omarchy-plugin-add:125), lenient for user data at runtime (Color.qml:198 skips unparseable lines; Menu.qml:979-983 loads the user menu extension and falls back to an empty list on failure instead of refusing the menu). Prompt files are user data, so lenient load with a visible per-file error list is the ecosystem-consistent pick; a team that wants strictness adds a validator in the repo's CI, not in the client. Keep "what the real prompts look like" as the only operator-owned item here.
