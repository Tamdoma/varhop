# Settings and hotkey: blind notes, slot C (2026-10-12)

Tiers: operator = INTAKE.md and Taken sections; better-than-training = inspected local source and live binding data, 2026-10-12; model-knowledge flagged where used.

## Facts inspected

- User bindings live in one user-owned file loaded after all Omarchy defaults: ~/.config/hypr/hyprland.lua:16-20 requires `hypr.bindings` after `default.hypr.omarchy` so "package updates can improve the defaults without rewriting your ~/.config/hypr files". There is no bindings directory that gets glob-loaded; a dropped-in file would never execute. The operator's own bindings.lua shows the override idiom: `hl.unbind(...)` then `o.bind(...)` per changed chord (:3-18). `o.bind` wraps `hl.bind` (helpers.lua:138-152) and `o.rebind` is unbind-then-bind (:154-157). A `{ panel = "ivan.varhop" }` table becomes `omarchy-shell shell toggle 'ivan.varhop'` (helpers.lua:99-100), because the zero-process GlobalShortcut fast path only covers ids listed in /usr/share/omarchy/default/omarchy/shortcuts (:20-21 has omarchy.clipboard/emojis), a package-owned first-party list a third-party plugin cannot extend. [better-than-training]
- Free chords, computed 2026-10-12 from the live system (`omarchy-menu-keybindings --print`, 242 chords parsed, cross-checked against `hyprctl binds`, 258 binds): every SUPER+CTRL letter for utility panels is taken except G, J, M, U, Y (utilities.lua:3,101-107; clipboard.lua:49). The P-for-prompt family: SUPER+P is pseudo-window, SUPER+SHIFT+P is Google Photos (applications.lua:32), SUPER+CTRL+P is Power; SUPER+ALT+P is free in both the stock defaults and this machine's live binds (modmask 72 + key P absent from `hyprctl binds`). SUPER+SHIFT+V and SUPER+ALT+V are also free; SUPER+V and SUPER+CTRL+V are universal paste and clipboard. Conflict evidence source: `omarchy-menu-keybindings` itself rebuilds this from `hyprctl binds` plus a Lua source scan, because Hyprland reports Lua binds as `__lua`. [better-than-training]
- No plugin registers its own hotkey or has a settings home. The installed third-party plugins (~/.config/omarchy/plugins/ivan.bar, ivan.clock, ivan.focus, ivan.monitor, ivan.notifications) are bar/bar-widget/service kinds; none writes a Hyprland binding, none is an overlay. Their settings live inside their own panels and persist via `updateEntryInline` (ivan.clock/Panel.qml:159-160). The only plugin-management UI is enable/disable/clone/remove (omarchy-menu-plugin); there is no manifest field for bindings or settings (omarchy-plugin-validate and shell/plugins/README.md contain no hotkey contract). PluginShellApi exposes summon/hide/toggle/updateEntryInline for the plugin's own id and nothing that touches Hyprland config. [better-than-training]
- Plugin lifecycle on disk: `omarchy plugin add` clones into ~/.config/omarchy/plugins/<id>, rescans, optionally enables (omarchy-plugin-add:145-175); enabling pushes `{id}` into shell.json `plugins[]` (PluginRegistry.qml:541). Disable and remove both call `setPluginEnabled false`, which splices the entire `plugins[]` entry out (PluginRegistry.qml:557), settings fields included; remove then deletes only the plugin folder and rescans (omarchy-plugin-remove:96-117). Neither script touches ~/.config/hypr, ~/.cache, or state files. [better-than-training]

## Q1 Global hotkey

Pick: the user pastes one line into ~/.config/hypr/bindings.lua. Settings and the plugin README show the exact line with a suggested default chord, SUPER + ALT + P:
`o.bind("SUPER + ALT + P", "Varhop prompts", { panel = "ivan.varhop" })`
The chord in the shown line is an editable text field in settings; editing it re-renders the line and a copy button puts the line on the clipboard (wl-copy, copy-and-close's transport). The plugin writes nothing under ~/.config/hypr and never reloads Hyprland. Conflict feedback: when the chord field changes, settings runs `hyprctl binds` once through a Process, parses modmask+key records, and warns inline if that chord is already bound, naming the existing description when Hyprland reports one. The line offered stays `o.bind`; a user who deliberately wants to steal a chord edits it to `o.rebind` themselves, using the helper that exists for that (helpers.lua:154).
Reason: bindings.lua is the user's own code, loaded last by design (Facts), full of hand-written functions and unbinds on this machine. It is the one file Omarchy guarantees updates will not rewrite. Paste-a-line is also the only mechanism that exists: no manifest contract, no bindings drop-in directory, no PluginShellApi for compositor config. SUPER+ALT+P is free on stock Omarchy and on this machine and P reads as "prompts".
Cost: first install has a manual step and the plugin cannot prove the user did it; detection is best-effort (code:-style binds and layout-dependent keysyms like the operator's `dstroke`/`scaron` binds can evade name comparison). Per press, the fallback spawns `omarchy-shell shell toggle` instead of using a registered global shortcut; that is the same path every third-party panel binding takes and the shell's IPC socket keeps it in the millisecond range (shell.qml:1653-1664 comment), but it is part of the pending form-factor proof.

Rejected:
- Plugin writes the binding (append a marked block to bindings.lua, or drop a file, then `hyprctl reload`). Reason: it must edit a Lua file containing arbitrary user code idempotently, guess where its block belongs relative to the user's own unbinds, and it acquires a cleanup duty on remove that the remove script cannot run (the plugin is disabled before deletion, omarchy-plugin-remove:96). A drop-in file is never loaded at all (Facts).
- Runtime registration (plugin runs `hyprctl keyword bind…` or declares its own Quickshell `GlobalShortcut` on load). Reason: runtime binds are not the file contract the keybindings menu reads, duplicate on every reload, and a GlobalShortcut still needs a Hyprland-side bind naming it, so the user writes a line either way, just a less standard one than `o.bind`.
- No suggested default chord; tell each user to invent one. Reason: the operator asked for a custom shortcut, not homework; a pre-filled free chord makes the paste step one decision ("keep or change") instead of a search through 258 existing binds.

Pitfalls:
- P1 The chicken-and-egg first run: settings cannot be opened before the binding exists. Remove: the plugin README carries the install sequence in order (add plugin, paste line, press chord), and first summon with no repo lands in settings (Q2), where the same line is shown for later changes. Documented fallback to open it without any binding: `omarchy-shell shell summon ivan.varhop`.
- P2 Duplicate bind if the user pastes twice or the chord was taken by a default they forgot. Hyprland then holds two binds for one chord and the preview in SUPER+K shows both. Remove: the settings conflict check above, plus README wording "if SUPER+K shows this chord taken, change the chord, don't paste twice".
- P3 The `toggle` in the generated command means the same chord hides the overlay (copy-and-close's hide path). Proof owed by form-factor: toggle on own id must route through the plugin's preserve-draft close, not an unload.

## Q2 Settings surface

Pick: settings is a view inside the varhop overlay, reached by Ctrl+, or a settings button in the search header; the repo picker is a subview of it. It holds exactly: gh status line (login name and scopes from `gh auth status`, or the missing/logged-out state with `gh auth login` shown as the fix, per sync-and-auth Taken); selected repo (`owner/repo`, private marker) with a Change repo entry into the picker (`/user/repos` list with its own filter field, plus the strictly validated typed `owner/repo`); Sync now button with last successful pull time and the last pull's error when it failed; library load errors as a count that expands to the per-file list from the importer; the hotkey section from Q1 (chord field, generated line, copy button, conflict warning); and a Reset usage data button that clears the whole usage file after an inline press-again confirm. Nothing else: no token field (sync Taken), no theme, font, or animation controls, no key rebinding grid.
Summon routing, in order: an existing draft resumes in the editor (copy-and-close Taken beats everything); no repo selection in the plugin's shell.json entry opens settings with the picker section focused; otherwise search, with cloning/empty/error states shown there per sync. An account-id mismatch discovered at pull or picker time routes to settings with the reconfirm prompt; it never hijacks a summon on its own.
Esc inside settings closes the settings view back to the stage it was opened from (picker subview first to settings top); Esc from a first-run forced settings hides the overlay with nothing chosen.
Reason: there is no other surface to put it in. No first-party settings center accepts plugin pages (Facts), and the plugins that exist keep settings in their own panels. The overlay already owns the repo picker and sync state, and first-run routing needs the picker one chord-press after install.
Cost: settings is only reachable while the plugin loads; a plugin broken badly enough to not open has no settings rescue path except editing shell.json by hand. Esc-as-close-view is a third Esc flavor next to search (clear-then-hide) and editor (hide); it matches how dropdowns/popups close in this shell (Ui/Dropdown.qml:179) but it is one more rule to state in the footer hints.

Rejected:
- An Omarchy menu entry for varhop settings. Reason: menu content comes from default/omarchy/omarchy-menu.jsonc plus the user's own extensions file (shell/plugins/README.md, Omarchy menu section); a third-party plugin cannot add itself, so this becomes a second paste-this-file burden, and the menu action would only shell out to summon the same overlay anyway.
- A separate bar-widget/panel kind in the same plugin for settings. Reason: a second entry point, bar placement decisions, and settings split from the picker/sync state they configure, for zero gain over a view switch.
- CLI/settings-file only (edit shell.json or a TOML by hand). Reason: the operator asked settings to "connect GitHub and choose a repo" (INTAKE.md); account reconfirmation and load errors need a visible home, not a file format.

Pitfalls:
- P4 Settings writes clobbering each other. Every write goes through the one settings object owner and `updateEntryInline` with the full object (sync Taken); the hotkey chord field is display/generation state and is not persisted, so it can never be the stale half of a full-object write. What settings shows as "current binding" is detected from `hyprctl binds`, not stored.
- P5 gh status is a subprocess with latency and failure modes. It runs when settings opens, not on every summon, with the sync fork's no-prompt environment and a timeout; the rest of settings renders before it returns.
- P6 Usage reset while a draft exists: allowed; it affects only future ranking and the empty-query recents. It must not touch the library, selection, or draft.

## Q3 Owed in-overlay keys

Pick, all intercepted on the focused native control in each stage (variable-editing's Keys-on-the-widget rule), none of them consuming ordinary text input:
- Ctrl+P "Find another prompt": editor → search, draft kept (its row carries the Draft marker). In search it focuses/selects the query field content as a no-op-ish "you are here"; in settings it leaves settings for search.
- Ctrl+Shift+P "Resume draft": search/settings → editor with the draft, the keyboard twin of search's pinned Resume action (search Taken). Absent a draft it does nothing. The pinned row's label prints this chord.
- Ctrl+R manual pull, every stage including the editor (draft untouched, sync Taken) and settings (same action as Sync now).
- Ctrl+, open settings, every stage; in settings it closes back to the invoking stage.
Reason: Ctrl+P/Ctrl+Shift+P is the quick-open pair users already have from editors [model-knowledge: VS Code and Sublime use Ctrl+P for file quick-open], P also mnemonics to "prompt", and the shifted form reads as the inverse trip without inventing a second letter. Ctrl+R is refresh everywhere, already locked by sync Taken. Ctrl+, is the cross-app preferences chord [model-knowledge] and collides with nothing taken: Tab/Shift+Tab, Ctrl+C, Ctrl+Shift+C (reserved as the Super+C-over-terminal spelling of copy), Ctrl+Z/redo, Enter, Esc are all untouched, and none of these chords is produced by Super+C/V/X/A forwarding (clipboard.lua:45-48 sends only Ctrl+C/V/X/A and their Ctrl+Shift terminal spellings).
Cost: four Ctrl chords to document in footers. Ctrl+P in a multiline editor would by default move the cursor up a line in some Qt configurations; varhop's editor accepts that loss, arrows remain. [model-knowledge]

Rejected:
- Ctrl+O for find-another ("open"). Reason: weaker launcher association than Ctrl+P and pairs badly (Ctrl+Shift+O has no reading).
- F-keys or Alt+letter chords. Reason: F-keys are laptop-media contended and Alt+letter risks menu-mnemonic expectations in text fields; the Ctrl family is what every other varhop action uses.
- Reusing Esc for find-another. Reason: foreclosed by copy-and-close Taken (Esc hides in the editor); this fork exists to not reopen that.

Pitfalls:
- P7 Stage scoping leaks: Ctrl+R or Ctrl+P typed into the repo picker's filter or the typed `owner/repo` field must not yank the user mid-typing. Remove: in picker text fields these chords are inert except Ctrl+, (closes settings); the picker has its own visible Sync/refresh affordance if needed. Leaf proof types each owed chord in every focusable field.
- P8 Ctrl+Shift+P vs Ctrl+P with slow modifier release: match on exact modifier state at key press (Control only vs Control+Shift), never on "contains Control", so the pair cannot double-fire.

## Q4 Lifecycle and what "customizable" covers

Pick: varhop cleans nothing automatically, because by the time removal runs the plugin is already disabled and cannot execute (omarchy-plugin-remove:96-103). What each action leaves, stated in the README and in settings' hotkey section:
- Hyprland binding line: stays, user-owned file. Pressing the chord after removal runs `omarchy-shell shell toggle 'ivan.varhop'` against an unknown id; the shell logs and does nothing. The user deletes the one line.
- ~/.cache/varhop (both clone slots): stays. It is a cache of a repo that still exists upstream; a reinstall reuses or reclones it. README names the path for manual deletion.
- Usage state file: stays, keyed by repo id (search Taken); if the same repo is chosen after a reinstall, frecency resumes where it left off. Reset usage data in settings is the in-app way to zero it while installed.
- shell.json `plugins[]` entry: the host deletes the whole entry, repo selection included, on disable and on remove (PluginRegistry.qml:557). Re-enabling recreates a bare `{id}` entry (PluginRegistry.qml:541), so the next summon is a first-run into the picker (Q2 routing). This is host behavior on the sync fork's chosen storage, and the fork should record it plainly: disable is not a settings-preserving pause.
"Customizable" in v1 means exactly three things: the user picks the global chord (any chord in their own bindings line), the user connects their own prompt repo in the taken format, and appearance follows the active Omarchy theme automatically (form-factor Taken). In-overlay keys are fixed, results and ranking have no knobs, and there is no settings surface beyond Q2's list.
Reason: every auto-cleanup alternative needs code running at uninstall time, and the lifecycle gives third-party plugins no such hook (Facts). Pretending otherwise in the chart would strand exactly the cleanup it promised. The remaining artifacts are small, named, and inert.
Cost: a removed varhop leaves a dead chord, a private-repo clone in cache, and usage timestamps on disk until the user deletes three known things. That is the honest price; U2 below offers the one mitigation fully in varhop's power.

Rejected:
- A plugin-shipped uninstall script the user is told to run before `omarchy plugin remove`. Reason: discoverability is near zero at the moment it matters, and `omarchy plugin remove` will not call it; a settings button (U2) reaches the same result while the plugin still runs.
- Storing the repo selection outside shell.json so disable preserves it. Reason: sync-and-auth already took `updateEntryInline` storage; reopening it here to soften disable semantics trades a settled single-settings-store design for a second store. Recorded as a consequence instead.

Pitfalls:
- P9 Reinstall resurrects stale cache. A cache slot built by an older plugin version is just a git clone plus index inputs; the importer must treat any slot whose recorded repo id or selection does not match as a fresh clone target (sync Taken's two-slot switch already provides the mechanism).
- P10 The dead binding after remove also fires on a *disabled* (not removed) plugin: summon on a disabled id warns and returns false (shell.qml summon path). Harmless, but settings/README should not promise the chord "stops working silently" in a way that implies an error state.

## Questions the fork does not ask

- U1 Should the suggested default chord be shipped at all, or is being told a chord part of the operator's "custom shortcut" intent? My pick suggests SUPER+ALT+P and treats customization as editing one field; if the operator already has a chord in mind, that field is where it goes, but the question of whose chord is "the default" in the README is theirs.
- U2 A "Delete local varhop data" button in settings (clear both clone slots and the usage file, keep the selection) is the only cleanup varhop can actually perform while alive. Worth adding for the private-clone-in-cache concern, or is naming the paths in the README enough?
- U3 Does the operator want a second global chord that summons varhop straight into settings (payload-routed), or is Ctrl+, after summon enough? The binding line can carry a payload through `shell toggle` only if the plugin's open() routes it; that contract is cheap now and awkward to add later.
- U4 When the plugin is disabled and re-enabled (selection wiped per Q4), should the picker pre-highlight the repo whose clone still sits in cache, as a one-click reconfirm? It softens the host's destructive disable without a second settings store.
