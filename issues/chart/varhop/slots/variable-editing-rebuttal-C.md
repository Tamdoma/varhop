# Variable editing: rebuttal C (disagreements only, 2026-10-12)

RC1. D-a editor mechanism: concede B's key-priority correction, hold the single-TextEdit mechanism with that correction.
- B is right on placement. Qt's key order is per item: forwardTo, specific handlers, onPressed, the attached item's own handling, then parent (https://doc.qt.io/qt-6/qml-qtquick-keys.html#key-handling-priorities, read 2026-10-12). A parent `Keys.BeforeItem` handler therefore runs only after a focused TextEdit has had its native turn; the PanelKeyCatcher.qml:23-27 comment I cited is wrong for keys the editor accepts. The handler attaches to the TextEdit itself, which is the shape that already works in panels/clock/Panel.qml:393,416 (Keys.onPressed inside each TextField).
- With that fix, the remaining B objection ("key restrictions cannot cover paste, mouse, IME") does not reach my actual proposal, which was key guard plus an `onTextChanged` verifier that restores the expected render for any change not attributable to the active range (variable-editing-C.md Q1, P2). Non-key mutations are exactly what the verifier is for.
- B's alternative (prose outside any writable model, own native input for the active value) is not specified far enough to prefer. A separate input overlaid on a read-only rendering cannot reflow the following prose when a value grows or wraps, unless the rendering below it is re-rendered on every change anyway, which reintroduces the same document the single-TextEdit design already has. One flowing TextEdit is the only proposed mechanism that gives inline multiline values, live mirrors, and one scroll/selection model.
- This is a mechanism dispute under an agreed behavior (values only, inline). It should not be an operator question. Settle it as a leaf done-criterion: whichever mechanism ships must pass the same proof (typing in prose rejected, paste by every route, dead keys, IME commit, multiline value, mirror edit).

RC2. D-b clearing: concede B's semantics (unset and filled-empty are different states; Delete on a value makes it empty). No separate reset key is needed: Delete or Backspace pressed again while the active variable is already empty is the reset to unset. One gesture family, no new binding for the shortcuts fork. The active empty target shows the variable name as dim placeholder text in the editor only; it is never in the rebuilt copy.

RC3. D-c Enter: withdraw my Enter = next stop pick. Enter inserts a newline, the native multiline behavior; Tab is the only navigation key, which is also the only one the operator locked (INTAKE.md). Espanso needed Ctrl+Enter to submit precisely because Enter means newline inside its multiline fields (https://espanso.org/docs/matches/forms/, read 2026-10-12). One less interception, no Shift+Enter special case.

RC4. D-d name grammar: concede B. `[A-Z0-9_]+`, no first-character rule. The repo-format Taken lists the character set only, A and C each invented a different first-char restriction, and one character-class rule is the simplest thing an author can be told. `{{2024}}` as a stop is harmless in a repo the operator authors to this spec.

RC5. D-e brace runs: hold A,C. A single left-to-right scan (or one global token pattern) gives `{{{NAME}}}` = literal `{` + token + literal `}` and `{{NAME}}}` = token + literal `}` with no special cases. B's "never match inside a longer brace run" makes `{{NAME}}}` entirely literal, which kills a real pattern: a prompt showing JSON-ish output ending in a variable, `{"answer": "{{ANSWER}}"}`, written without the inner spacing, or any token directly before a literal `}`. The author who wants triple braces literal already has `\{{`. B's rule needs extra boundary checks in the scanner to protect authors from a case the escape already covers.

RC6. D-f undo: concede B. Semantic per-variable undo/redo (value and unset/filled state, mirrors follow, reset included), no cross-variable undo. Document undo in the TextEdit cannot be exposed once mirror patches are programmatic edits in the same document.

RC7. Value fidelity (merged "Raised", B Q10/R9): concede the fact, dispute the recommendation. B is right that my Q4 overclaimed: rebuilding preserves the stored template literals exactly, but a value is read out of the editor, so pasted CRLF becomes LF and NBSP becomes a space in values too (B E10; QML's TextDocument wrapper exposes no raw-text accessor, https://doc.qt.io/qt-6/qml-qtquick-textdocument.html, read 2026-10-12). But the verbatim lock covers prompt bodies (forks/repo-format.md:28), not user-typed values, and the normalized differences do not change what a pasted prompt says. State it plainly in the fork ("values enter as the editor holds them: LF line breaks, NBSP read as space") and close Q10 as accepted for v1, rather than leaving a "separate proven input boundary" pending for fidelity nobody locked.
