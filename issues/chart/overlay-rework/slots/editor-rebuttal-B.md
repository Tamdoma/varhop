# Slot B editor rebuttal

- **R1. The C++ conclusion overstates my evidence.** I said QSyntaxHighlighter requires a native subclass and that its documentation does not establish a QML-only implementation. I did not prove that every form of per-range visual styling requires C++, or endorse adding one. Separate native document formatting from decorations painted outside the document. Likewise, “no compiled extension” is my recommended scope, not an existing operator decision established by my notes.

- **R2. M2 is a candidate for reconsideration, not an automatic fallback.** My notes explicitly reject silently changing mechanisms after a failed probe. Replace the attribution “A and B fall back to M2 if M1 fails” with “B would reconsider M2 if M1 fails.” I retain a 20-minute probe of M1's disqualifying cases as the default recommendation. A 60-minute comparison of both is a different proposal the operator can choose, not consensus. Failure or timeout should produce a finding and a mechanism decision, not implicitly authorize another implementation or a hybrid.

- **R3. Q2 records unproved geometry and an unspecified size as agreement.** I recommended unobtrusive decorations and a small non-text empty-range indicator, conditional on layout testing. I did not specify a one-character-wide marker or establish that positionToRectangle alone supplies correct per-line range rectangles. A painted empty marker must not obscure adjacent prose or other empty variables. Wrapped ranges, adjacent empty names and font changes must be measured before calling this rendering recipe settled.

- **R4. The recommended M2 pass bar is weaker than M1's.** “Wrap, multiline and empty cases stay usable” does not establish the locked input/history/resume behavior. If the operator chooses to probe M2 too, test its selection replacement, native menu Undo, composition, mirror synchronization and per-name history as well as geometry, or mark those paths unproved. Reusing a native field does not prove that repositioning it and writing the canvas on each edit preserves those behaviors. Neither prototype can substitute for the final-build criteria already selected in the proof-bar fork.
