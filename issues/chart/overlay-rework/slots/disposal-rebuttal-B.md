# Slot B disposal rebuttal

- **R1. The old worktree does not need removal under the distinct-slug proposal.** The merged notes say it must be removed “either way.” `next.ts:310` derives the worktree path from the successor slug. A new slug gets a different path and can adopt its own branch created at `0df6f48` through `next.ts:325-333`, while the old branch/worktree remain intact. My recommendation explicitly retains the original until the successor is verified. Reusing the old slug/path needs separate handling. Correct this before presenting retirement steps.

- **R2. “Then plugin update + restart” omits the update-source check.** Keeping the installed copy is my recommendation, but I did not endorse an unconditional update command. A clean installed clone at the right revision does not establish that its remote will deliver the successor branch. Before moving/removing the old worktree or promising the replacement rollout, inspect the installed remote and branch tracking, establish the replacement source, and verify the deployed revision afterward. This was R8 in my notes. Preserve the existing selection and user data through the chosen rollout.

- **R3. Branch adoption does not itself require every parallel leaf to wait for the first merge.** One completion owner remains my preferred split, but the merged statement “only one leaf can adopt the branch, so any parallel split waits for the first leaf to land” overstates the mechanism. Distinct slug branches can start at the same retained commit using the inspected adoption path. Whether separate leaves should do that depends on ownership of the shared unmerged baseline and their actual dependencies. Present first-leaf landing as a proposed ownership strategy, not an akrogon constraint proved by `next.ts:325-333`.
